## Cleanup run (release-engineer)

The release engineer reads this file only when main launches it for post-merge cleanup or authorized retirement. Placement, ownership and the routine retain rules are in `index.md`.

**Post-merge worktree cleanup.**
After a verified merge, act only on the exact task-owned worktree list supplied by main. Inspect integrated commits and tracked, untracked and ignored state; retain any target whose unique or unreproduced required evidence or user data is not preserved. Remove only clean, integrated, idle checkouts with `git worktree remove` using the exact absolute path, without `--force`, then verify both folder and registration are gone. Retain and report dirty, unmerged, active, unknown or user-owned checkouts with concrete reasons. Never remove your own active cwd or a checkout used by another running/paused worker or server. Missing terminal/quiescence evidence means RETAINED / CLEANUP_PENDING, not inferred approval. In routine mode there is no reset, clean, force-removal, branch deletion, wildcard, sweep or arbitrary directory deletion. In routine mode the only removals are the exact checkout (`git worktree remove`, no `--force`) and the exact `_evidence/<task>` and `_scratch/<task>` directories the packet names, each by the packet's exact host-appropriate removal operation, one exact path at a time (canonical detail: `worktree/index.md`). Readiness or role guidance never authorizes merge, release or destructive cleanup.

**Automatic checkout cleanup.**
When main launches you with a runtime `cleanup` scope (cwd = the primary, outside the target), the runtime appends a RUNTIME CLEANUP SCOPE block to your task with the merged PR, the exact targets in order and their exact commands: that block is the authorization, so follow it without asking main for commands, and with no block (or NOT RECEIVED) remove nothing and report BLOCKED with that reason; with no block at all, also say the Pi session may have loaded the harness before an update (skills are read from disk, extensions once per session), so main should ask the operator to run /reload and launch the cleanup again. For a worktree task, run exactly `git worktree remove "<exact absolute path>"` once, then verify folder and registration are gone. The guard re-verifies the live merged PR, a clean checkout with no ignored content and the exact form; a refusal means RETAINED with the reason, so stop and return BLOCKED without retrying. Then, once the knowledge checkpoint is SAVED outside every target or NO LESSON, remove that task's `_evidence/<task>` and `_scratch/<task>` folders, each exactly once with `rm -rf "<exact absolute path>"` (bash) or `Remove-Item -LiteralPath "<exact absolute path>" -Recurse -Force` (PowerShell), cwd = the primary; the guard allows each only after the checkout and its registration are gone, within 10 minutes of main's approval, and when the folder holds no symbolic links, junctions, special files or nested repositories (hard links from build output such as `target/` are fine). A refusal names its reason (form, scope, already used, expired, cwd, or what the folder holds); report it as given. A missing folder is ABSENT; a refusal means RETAINED with the reason. If a removal fails partway and the same folder is still there, run the same exact command again (at most 3 attempts in all), then report RETAINED with each error. Use is judged for each exact target, not the machine. A process blocks a target only on confirmed use: its working directory, its command line or a file it holds open lies inside that target. A process with no such reference, such as an unrelated dev or test server, does not block, and is not stopped or restarted for the cleanup. Being unable to list a process's open files is not unknown use by itself: when the runtime's worker records for the target are terminal and no process references it, run the removal. The removal is the last check: a held file or lock makes it fail (on Windows the delete is refused while a handle is open), so report that failure exactly (the command, its error text and what remains) as RETAINED, and confirm the target is absent afterwards. For a plain-branch task (the candidate was the primary checkout) the scope carries a task instead of a checkout: there is nothing to remove first, so remove only its two artifact folders the same way. Your reports and temp files stay outside every target.

**Authorized retirement.**
This separate mode applies only when the packet carries user-disposition authority naming each exact absolute path or data item and the exact operation; merge, readiness or general cleanup never selects it. Dirty or unmerged drafts are disposable only with explicit discard consent for that exact path. Only then may you force-remove the listed discarded checkouts and afterwards the exact approved retired parent, once all nested registrations are removed and confirmed. Reject active, paused, service, live database, unknown-owner or new ongoing data; never touch the primary checkout or artifacts outside the targets or remove your own cwd. Existing guard refusals and operator grants stay required, with a local SAVED or NO LESSON checkpoint outside every target. Verify exact absence, registration absence and protected data afterwards; any failure stops remaining operations with a partial report. Canonical detail: `worktree/index.md`.
