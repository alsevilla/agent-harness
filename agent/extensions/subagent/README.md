# Pi subagent extension

Run named specialists in isolated Pi subprocesses while keeping the main conversation available. This profile supports only the latest Pi release (see the [root README](../../../README.md#status-and-limits); earlier versions are historical observations) and uses the 21 definitions in `~/.pi/agent/agents/`; these are the installed roles, not the upstream example's planner/worker set. The release engineer owns only selected SHIP/LEARN work.

## Dispatch and results

The orchestrator calls `subagent` with one of these shapes:

| Mode | Parameters | Behavior |
| --- | --- | --- |
| Single | `{ agent, task }` | One named role |
| Parallel | `{ tasks: [{ agent, task }, ...] }` | Up to eight tasks, four subprocesses at a time |
| Chain | `{ chain: [{ agent, task }, ...] }` | Sequential steps; `{previous}` inserts preceding output |
| DAG | `{ dag: [{ id, agent, task, cwd?, dependsOn?, readOnly? }, ...] }` | Up to eight nodes; a node starts only after its direct parents are accepted |

DAG mode is exclusive with single, parallel and chain: an empty `dag` array counts as present, and any ambiguous, missing or invalid mode returns `isError` before any launch. In DAG mode, any top-level key that is not one of the tool's own parameters (for example a typo such as `agnet`) also returns `isError` before any launch. Node IDs start with a letter and use letters, digits, `_` or `-` (max 32), must be unique, and `dependsOn` must name existing nodes (no self, duplicate, missing or cyclic edges). Every `agent` must be a discovered role. A node is accepted only when it is not a failed result (exit 0, terminal `stop`, no error or abort). Each direct parent's full final text, with any `ERROR:`/`STDERR:` lines, is appended to a child's task under `--- Report from parent node "<id>" (agent: <agent>) ---`, concatenated literally. Failed, errored, `length`-stopped or blocked nodes block their descendants (`BLOCKED by <ids>`); independent branches continue. At most four nodes run at a time, each through the same workspace claim, provider check and declared fallback as a single run. The graph result is `isError` if any node is not accepted, and results are listed by node ID with status and cause. Abort or cancel launches no new nodes, drains running children before the job settles, and reports completed nodes honestly; nothing is rerun. Pause holds the whole job, including nodes not yet launched. `readOnly` is a trusted caller declaration, not an OS sandbox. DAG state is process-local to the session's job list: it is not persisted and not shared across Pi processes. Adaptive concurrency, duplicate coalescing and persistent graphs are not implemented (roadmap V3.2/V3.3 not done). Foreground DAG runs show no live per-node progress. A DAG result is evidence for the orchestrator, not an approval; core and manual review still apply.

### Optional Pi task model tiers

Pi callers may set `modelTier` to `"economy"` or `"capable"` for a single task, or on each item in a `tasks` (parallel), `chain`, or `dag` batch. For single mode it is a top-level parameter; for batches it belongs to each item/node. These four forms work with the default background job (`background: true`) and with `background: false` foreground execution. Omit the field to run the role's `defaultModelTier` with that tier's own model, fallback and thinking. A root-level tier is not accepted for batch modes.

Each canonical role's tier presets live in Pi's existing `agent/roles.json` beside its `tools` field. `defaultModelTier` names the tier used when `modelTier` is omitted. This is the shipped `backend-worker` entry, as an example of the shape:

```json
{
  "name": "backend-worker",
  "defaultModelTier": "economy",
  "modelTiers": {
    "economy": {
      "model": "openai-codex/gpt-6-luna",
      "fallbackModel": "anthropic/claude-haiku-5-5",
      "thinking": "medium"
    },
    "capable": {
      "model": "anthropic/claude-sonnet-5-5",
      "fallbackModel": "openai-codex/gpt-6.1-sol",
      "thinking": "medium"
    }
  },
  "tools": "read, grep, find, ls, bash, powershell, edit"
}
```

Use the actual presets in `agent/roles.json` as the source of current model identifiers; this guide intentionally does not maintain a second model table. Any canonical package role whose `modelTiers` are configured accepts explicit `economy` or `capable` requests. There is no role allowlist, no new role is created, and a task cannot supply a model ID, provider, fallback or thinking value. An explicit tier the role does not configure is refused before launch. Project agents and custom/user shadow definitions reject an explicit `modelTier` before any task launches; an omitted tier still runs that definition's own default.

Each tier object has exactly `model`, `fallbackModel` and `thinking`. `model` is one `provider/id` string passed verbatim (no alias or Copilot mapping). `fallbackModel` is `""` for no fallback, or ordered `||`-separated `provider/id` models (trimmed, duplicates removed). `thinking` is one of `off`, `minimal`, `low`, `medium`, `high` or `xhigh`. The profile does not verify that a given model accepts a given thinking level, and no level is clamped. `tools` stays on the role; tiers cannot change tools, permissions or role ownership. `defaultModelTier` must name a configured tier. Main chooses the cheapest tier judged sufficient; the runtime applies no numeric tier policy and no automatic upgrade.

A batch is resolved as a whole before any job, workspace claim or child spawn. A value other than `economy` or `capable` (including `null` or an empty string), an explicit tier the role does not configure, or an explicit tier on a user, project or shadow source at any position refuses the entire batch with zero children. A role whose default tier is not configured is unavailable. A background chain keeps the tier admitted for each step, so a later `roles.json` edit does not change a step already admitted.

### Optional explicit fallback slot (`modelSlot`)

An entry may add `modelSlot: "fallback"` beside an explicit `modelTier` (single mode at the top level; in `tasks`, `chain` and `dag` per entry; a root `modelSlot` on a batch is refused). The only accepted value is the string `"fallback"`; omission is the ordinary behavior, and `null`, other values or a slot without an explicit tier are refused before any spawn. It applies to canonical package roles only. The task starts directly on the first configured fallback of that role's same validated tier (the exact primary is excluded), keeps the tier's thinking and the role's tools and permissions, and gets an empty replay chain: there is no synthetic failure, no `failed; retried` text, and no return to the primary or a later fallback after a quota, cooldown, task, tool or abort outcome. It is refused before launch when the role is not a package role, the tier is not configured, or the tier has no usable fallback. It cannot supply a model ID, provider or thinking value, the Anthropic subscription guard still applies to an Anthropic fallback, and stop, pause, admission and permission controls are unchanged. Results, background listings, the monitor and handoff headings show `slot: fallback` beside the tier and the model provenance below; ordinary runs carry no slot field.

A fallback is not automatically cross-provider: it differs from the primary only for that role's own configuration, so read the observed provider/model in the result (see Model provenance). Whether provider diversity is required is main's explicit per-task gate. Copilot is unsupported (it has no `modelSlot`, inherits the session model and does not read `roles.json`). Reload Pi or start a new session before the new tool schema is available; the offline routing evaluator accepts the same field and requires the explicit tier. Static and unit tests do not prove live provider behavior.

#### Model provenance: requested vs observed

A launch request is never evidence of what ran. Each result keeps `requestedModel` (that attempt's `--model` argument) apart from `observed`, the distinct `{provider, model, responseModel?}` identities the child's own assistant messages reported (first-seen order). `model` is the latest complete observed effective id with `modelSource: "observed"`, so a contrary observation is never hidden by the request. "Observed" means an observed child message, not a served-model attestation: in Pi 1.3 `AssistantMessage.provider`/`model` echo the child's request (its route provider and the id it sent), and only `responseModel` can evidence a differing served id. The effective id is the route provider plus `responseModel ?? model`; a `responseModel` equal to `model` is dropped, and the upstream provider is never inferred from `responseModel` text (a router keeps its route provider). A textual alias/snapshot difference is reported as `MISMATCH` with `[response id; sent <model>]` but is not a verdict of a different underlying model. `responseModel` is set by only the `anthropic-messages` and `openai-completions` producers in Pi 1.3.0, so its absence (other APIs, an unreporting backend, or a failed/aborted message before any response) is labelled `served UNVERIFIED` and never read as served equality; `servedReported` in `subagent_control list` is true only when `observedModels` is non-empty and EVERY row (partial and unknown ones included) is complete with one. `MIXED` counts distinct effective ids across completed messages, not metadata such as `responseId`. The monitor takes identities only from `message_end`, the authoritative final message on the `--mode rpc` wire. With no complete observation it stays the request and `modelSource` is `"requested"` (requested-only, unobserved). A report missing provider or model is kept in `observed` as partial and never counts as observed; provider is never inferred from the request. A completed assistant message that reports no identity at all is kept as an empty `{}` marker (at least one unknown completed message, not a message count), so a served report on another message never verifies the attempt; it never replaces `model`. After an availability fallback `attempts` lists every launched attempt (its own request and observations, earliest first; the trail also shows a lone prior attempt and marks each attempt's own partial/`served UNVERIFIED` state), so the final request is not mistaken for the role's original configuration; a launch skipped for provider cooldown never ran and is not an attempt. Retained/handoff headings print `model: <effective id> (observed[, MIXED][; MISMATCH, requested X][; served UNVERIFIED])` or `model: <request> (requested-only, unobserved|partial report ... UNVERIFIED)`; `subagent_control list` workers carry `model`, `modelSource`, `requestedModel`, `observedModels` and `servedReported`; the monitor labels its Model line the same way.

No runtime checker enforces provider diversity. When main selects a cross-provider check as an explicit gate, it compares the observed providers across the whole review (every `observed` entry and every `attempts` entry, not only the last): missing or partial observation is unverified, not a pass, and a requested or configured provider never substitutes. Provenance is limited to what the child's messages reported; it is not a provider attestation.

Legacy flat user entries (`provider`, `model`, `fallbackModel`, `thinking`) still load for compatibility. They have no tier, so an omitted request runs their flat values and an explicit tier is refused. The profile does not migrate files on disk and does not clamp values. For example, a single-task request is `{ "agent": "backend-worker", "task": "...", "modelTier": "economy" }`; parallel, chain and DAG callers put that field on the specific task, step or node instead.

The selected tier is resolved once per logical task, before any job, admission or spawn. Its own configured fallback sequence is used only for provider-availability failures before tool activity; there is no task/tool/abort replay and no automatic upgrade from economy to capable. Permissions, tools and role responsibility remain those already declared for the role. Tier selection is Pi-only; Copilot CLI's native model defaults and API are unchanged, and no Copilot tier parameter is provided. The native Copilot agent headers carry no model, so Copilot inherits the outer session model (see the root README's Copilot preview boundary); they keep native `tools` aliases that are not mapped to Pi tools and are not read from these tiers. No model-quality, cost-saving or billing claim is made for either tier.

For tiered roles, existing task diagnostics include the resolved tier and actual model, whether the tier was explicit or the role's default (the label does not say which); background label forwarding is not separately verified; `/subagent usage` continues to use the existing settled-task counters, reported token usage and provider/catalog-estimated costs. Missing usage or cost remains unknown/unpriced; these estimates are not billing. Roles without tiers keep their existing diagnostics and output.

Supply the absolute candidate `cwd` and a self-contained task packet: requirements, evidence, permitted mutations and acceptance checks. For artifact-producing tasks, include exact absolute `_scratch/<task>` and `_evidence/<task>` paths even when editing the primary checkout; code-role guidance instructs leaves to return missing paths instead of inventing sibling folders. It warns against relocating live SQLite data or running executables before an authorized stop. Unknown restart configuration does not block authorized relocation; it blocks restart until executable, environment and DB path are verified. Children do not inherit the main conversation. User definitions are the default; project agents in `.pi/agents/` require `agentScope: "project"` or `"both"`. Project definitions override matching user names under `both`.

Runs are background jobs by default. A `bg-N` receipt acknowledges dispatch; it does not prove implementation or testing finished. Completion results arrive automatically without polling model calls. `background: false` requests a blocking run: the task travels to the child as its RPC stdin prompt (never on the command line, so large tasks keep their exact bytes), the call returns the final result synchronously with no job receipt, and background steering does not apply. Successful background receipts are hidden in collapsed main-screen history; expanded history can show the job ID. Errors and foreground results remain visible. Automatic background completion notices are capped at 4,000 characters; a longer one begins `INCOMPLETE HANDOFF`, names the job ID, and must not be accepted from its excerpt. `subagent_control` `result` returns the complete retained child reports (every text block of each child's latest text-bearing message, with `ERROR:` lines for failed or stopped children). Foreground results are not capped and use the same complete final-text extraction; failed foreground children add their distinct stderr and partial text after the error line. Chain `{previous}` receives the complete previous final text. Child system prompts for roles with a prompt body receive the handoff format from `compact-handoff.ts` (guidance only; it does not change tools, models or exit status). The `subagent` tool description lists role names only.

For user roles, `roles.json` is canonical for `defaultModelTier`, the `modelTiers` objects (`model`, `fallbackModel`, `thinking`) and `tools`; the definition file in `~/.pi/agent/agents/` keeps only its identity, native Copilot `tools` and prompt body; it carries no model or `pi.*` mirror. An external legacy definition that still carries those values must match the default tier. Canonical package roles require their `roles.json` model and tools and fail closed without them; they never inherit a header model, the session model or the host's full tool set. Project roles in `.pi/agents/` use their own frontmatter. A `fallbackModel` (tier or legacy) accepts a single model or an ordered `||`-delimited chain. Each member is trimmed; empty, duplicate, and exact primary-model entries are skipped. The finite chain is attempted in order only for provider-availability failures before any tool activity. Task errors, aborts, and errors after tool activity are never retried. Native GPT IDs, including `gpt-6.1-sol`, are preserved. Model IDs are passed verbatim, so literal `claude-sonnet-5-5` and `claude-sonnet-5.5` are not rewritten to `claude-sonnet-5`; provider availability remains an external requirement.

## Workspace admission

Single, parallel, chain and DAG launches, foreground or background, share one process-local admission. Each run resolves its `cwd` to a canonical checkout (`realpath`, then the nearest ancestor with `.git`), so a subdirectory or junction of one checkout uses the same claim queue. A run acquires its claim before the provider check and before spawning; a run cancelled while queued spawns nothing. Access defaults to `write` (exclusive). A DAG node with `readOnly: true` requests `read`, a trusted caller declaration that is never inferred from tools or the shell. Readers share a checkout; a writer waits for and excludes everyone; a reader queued behind a waiting writer also waits (FIFO, no reader barging). Release is token-fenced. Background jobs also share a four-slot capacity per Pi process, and a paused job that is still queued releases its slot. The queue is process-local: it does not coordinate separate Pi processes or machines.

## Live inspector

The main panel is hidden until workers exist. It shows session totals and active worker rows:

```text
Workers · 1 active · 2 spawned · 1 done · 0 failed/stopped
#2 frontend-worker · gpt-6-luna · low · Finish the UX checkpoint
```

Finished rows disappear from the main panel but remain in bounded inspector history. Bare `/subagent` in TUI opens a three-entry menu: `Inspect workers (N)` (first, preselected), `Edit roles` and `Create agent`; Esc does nothing. `/subagent create` (or the menu entry) is operator-only: it asks for an absolute project root and spec JSON file, previews through the agent-creation Node CLI (`create-agent.mjs`), and creates files only after an explicit CREATE (Cancel is first). It is not a model tool; nothing is reloaded, trusted or launched, and created agents are not active until used with `agentScope` project/both. With no workers yet, Inspect notifies `No subagent workers yet.` Ctrl+Shift+W opens the inspector directly, and clicking a worker opens it too. The bordered overlay shows role, model, effort, status, task, activity, context and elapsed time. Statuses include Initializing, Ongoing, Pausing, Paused, Completed, Failed and Stopped.

Activity uses native Pi assistant/tool components in chronological order. Latest output appears at the bottom. Scrolling up pauses following; End/Ctrl+End or **Jump to latest message** resumes it. Home/Ctrl+Home goes to oldest retained activity. Page keys and mouse scrolling follow Pi keybindings. The inspector's scrollbar follows the main `fullscreenScrollbar` setting (`auto`, `always` or `hidden`) and supports the same mouse hover reveal, click-to-jump and thumb drag as Pi's transcript scrollbar. Ctrl+O or clicking a turn controls native expansion. Worker selection and reopening preserve per-worker reading position.

Escape or a primary click outside the overlay closes it without stopping workers. Mouse controls require terminal mouse support. The outside-click adapter depends on Pi's TUI listener internals and must be checked after upgrades. This is a terminal overlay, not an operating-system window.

History retains up to 40 tool calls and 120 transcript entries per worker, and 64 finished attempts per session. Only these retained finished jobs can be recovered with `result`; this is not a durable archive. Private thinking text is hidden. Context is the latest reported request size, not cumulative spend. Integration counters summarize observed calls/errors and graph-artifact reads; they do not certify correctness or measure Ponytail's injected prompt.

## Steering, pause and cancellation

Use `subagent_control` actions `list`, `steer`, `pause`, `resume`, `cancel`, `result`, `decisions`, `answer` and `decline`. Commands provide the same controls without a model call:

```text
/subagent list
/subagent steer #2 Focus only on the remaining fixture; preserve existing edits.
/subagent pause bg-1
/subagent resume bg-1
/subagent stop #2
/subagent result bg-1
/subagent usage
```

`/subagent usage` is command-only: it prints one notice and changes no footer, widget, menu or session entry. It counts every delegated agent task this Pi run (one per single run, chain step, parallel task or DAG node; one `bg-N` receipt may cover several; foreground and background shown as separate subtotals). Counters are in memory only and reset on reload or session change; an agent task that settles after a reset charges only its own launch scope. An agent task counts once when it settles (completed, failed or aborted); its physical fallback attempts are counted once each. Pending agent tasks, including queued ones, are excluded until they settle. Costs are the provider or catalog figures as reported, not a bill; unpriced turns are excluded and counted, and a zero cost with tokens is labelled as possibly unpriced, not free. Native footer accounting is unchanged.

#### Usage views and telemetry (Phase 1)

The plain `/subagent usage` notice above is unchanged. These views add to it (command-only, numeric data, in memory):

| Command | Shows |
|---|---|
| `/subagent usage --by-role` | Per role: settled tasks by status, turns average and p50/p95, peak prompt p50/p95 (with count of tasks that reported usage), output total and per turn, cost total and average over priced tasks. |
| `/subagent usage --top N` | The N most expensive settled tasks (`t-N` ID, role, tier, status, turns, first-turn and peak prompt, output, cost, observed model). Unknown cost ranks last. |
| `/subagent usage --main` | Main session: turns since session start and since the last compaction, last turn's prompt components, peak prompt, context estimate against the main model's window, totals including cache-tier cost, auxiliary usage. |
| `/subagent usage --planner` | Planner consultations (`cons-N`): counts, trigger, task, advice, settled tokens and cost, pending state. |

One view per command. `--top` takes a positive whole number (`--top 0`, `--top -1`, `--top 1.5` and `--top` alone are refused with the expected form). An unknown option is refused with the list of valid options; before this change, text after plain `usage` was silently ignored.

Metric formulas. Prompt tokens of one request = `input + cacheRead + cacheWrite` (the Pi usage fields are disjoint; cached context is `cacheRead` and `cacheWrite`). Output and reasoning are never part of a prompt. A task's first-turn prompt is the prompt of its first finalized turn (null when that turn reported no usage); its peak prompt is the largest prompt over every turn of every fallback attempt that reported usage. Turns, output, input, cache and cost sum every attempt once; a settled task is counted once. Cost is the SDK-reported cost of priced turns; a task with no priced turn has no average cost.

Percentiles use the nearest-rank convention: for `n` values sorted ascending, p is the value at rank `ceil(p/100 × n)` (1-based). Turns percentiles include tasks with zero turns (for example, a task aborted before its first turn). Peak percentiles exclude tasks without reported usage. With no value, the field is `n/a`, never zero; with no settled task, the view says so.

The configured model is the first attempt's requested model; the observed model is the served identity the final attempt reported, shown only when reported. Each task has a stable `t-N` ID, unique within the runtime process (it does not restart after a session reset).

Main-session telemetry comes from native events only: `turn_end` assistant messages (one turn each), `session_compact` (threshold, overflow or manual compaction), and `session_start` (rebuilt from the session branch on startup, reload, new, resume and fork; cleared on shutdown). Auxiliary usage entries (cache warming, compaction summaries and branch summaries) are read from the branch at display time and are not turns. The context estimate is the runtime's `getContextUsage()` and is labelled as an estimate; the window is the actual main model's `contextWindow`, never a child's model. A missing estimate or window is shown as unavailable.

Planner consultations are telemetry only. A single launch of the `planner` role may carry `consultation: { trigger, taskId? }`: `trigger` is a 1-64 character token (letters, digits, `.`, `_`, `-`) naming the reason, and `taskId` is an optional top-level task identifier. Without `taskId` the consultation is counted as unassigned, never as a task. The launch text (or the background acknowledgement) names the `cons-N` ID. Main records its decision with `subagent_control` `action: "advice"`, `target: "cons-N"` and `advice: "accepted" | "rejected"` (last write wins; unknown IDs are refused). A consultation with no recorded advice is `unknown`; one with no settled planner task is `pending`. The runtime never decides when to consult and never acts on advice.

Storage and retention: the ledger keeps one numeric record per settled task and per consultation for the current usage scope. It stores no prompts, messages, task text, tool output or conversation content. It is cleared with the existing usage reset (session start, reload, new, resume, fork and shutdown); a task that settles after a reset is charged to its launch scope only. Phase 1 adds no limits, so no `roles.json` setting or per-packet override exists for these views. Policy versus runtime: the views, percentiles, consultation metadata and advice storage are runtime behavior; whether main consults the planner, and what it accepts, is model-followed policy recorded as telemetry only.

Bare aliases `/engineering-harness` and `/agent-creation` only queue the native `/skill:engineering-harness` and `/skill:agent-creation` commands with the trimmed arguments; they create nothing, change no agent or role, and `/subagent create` remains the operator creation path. The explicit `/engineering-harness` alias intentionally expands the full skill entry again; do not invoke it on every ordinary task as a cache. Reuse already-read, unchanged guidance in the same active context, and selectively reread the required skill/module if compaction loses it or it changes. Each worker has an isolated context and loads its own applicable guidance once. `/reload` refreshes resource/configuration catalogs, not ordinary skill guidance, and revokes in-memory authorization grants: settle active workers first. Native bundled-harness references resolve from the canonical installed package root; optional skill catalogs require available files/resources. Native compact-policy recovery was historically SDK-tested through the real compaction API on Pi 1.1.0 and 1.2.0, and the offline regression runs it against the selected host release; this does not guarantee model retention or compliance. No persistent cache or runtime loaded-skill registry is claimed. If another command already owns either bare name, the alias is disabled with a warning at session start; the `/skill:` form still works.

`/subagent roles` (also the bare-menu entry `Edit roles`) opens native dialogs to change one user role's default tier model, ordered fallbacks and thinking level; other tiers are kept. Without a UI, bare `/subagent` prints a one-line hint of the existing commands instead of a popup. The edit writes roles.json only: a header-free definition is never rewritten, and only an external legacy definition that still mirrors model, fallbackModel and thinking has those lines updated. Choose a role, then a primary, fallbacks (add, remove, move) and a thinking level supported by the chosen primary. Choices are connected models only: installed catalog entries whose provider has explicitly configured credentials (no subscription or refresh check). With no connected model, it notifies you to `/login` or set a provider API key and changes nothing. The current primary is always pinned first as `Current <provider/model>` with its access suffix (` (not connected)` or ` (not in installed catalog)` when applicable), and is not repeated in the catalog list; choosing it changes nothing until you confirm Save. A saved fallback that is not connected stays visible with its suffix and keeps its exact value unless you change it. In TUI the menus and the save preview use the subagent window frame; the preview has explicit Save and Cancel. The preview shows before/after values and warnings (uncredentialed or out-of-catalog models, fallbacks that clamp the thinking level); nothing is written until you confirm. Only the role's default tier `model`, `fallbackModel` and `thinking` in `roles.json` change (`defaultModelTier`, other tiers and `tools` keep their values). In an annotated definition only its `pi.model`, `pi.fallbackModel` and `pi.thinking` lines change, so the native root `model` stays as written; an unannotated legacy definition has its `model`, `fallbackModel` and `thinking` lines rewritten instead. If an annotation disagrees with `roles.json`, the editor refuses that definition. Name, tools, permissions, description and prompt body are untouched. Non-default tiers are edited directly in `roles.json`. It refuses without a UI. It refuses to rewrite any file that is not valid UTF-8, and refuses missing, malformed, duplicate, ambiguous or non-canonical definitions and `roles.json` (every sibling entry must carry all five fields). It refuses symbolic links and Windows junctions in the profile path, the `agents/` directory, `roles.json` or the definition, and refuses `roles.json` or the definition when it has a second hard link; these are checked before preview and again at commit. A thinking level that the primary no longer supports is refused unless you pick a supported one; an unchanged legacy level stays selectable, labelled as unsupported, and is saved only when you keep it. Each target is staged before the first replace, so a staging failure changes nothing; a failed `roles.json` replace rolls back our own definition bytes only when the file is still ours. Jobs already accepted keep their configuration; new jobs read the saved settings. It does not refresh models or check credentials beyond the installed registry. The two-file commit is not atomic: a crash or an outside edit between the two replaces can leave them inconsistent, and recovery bytes are reported in the failure message.

Steer targets a job or worker. With exactly one active worker it goes to that worker; with several active workers the call lists their IDs and asks you to pick one. With no active worker (between chain steps or DAG nodes) the message is queued on the job and sent when the next worker starts; the reply then reads `Queued until the next worker starts; not acknowledged yet` until that happens. Steering is applied between tool turns and does not interrupt a running command. Pausing is enforced by the child-only `pause-gate.ts`: current tool/model calls may finish, then the next tool, provider or settlement boundary waits locally. A paused job also holds subsequent chain steps. The parent distinguishes Pausing from confirmed Paused. Resume continues the same process/context; cancel terminates it. New dispatches cannot bypass paused jobs/roles.

Literal steering phrases such as `stop for a bit` are converted to pauses; use explicit pause controls for other wording. Temporary control files are cleaned up when workers exit. Session reset/shutdown cancels owned background jobs.

## Worker decisions

A new background worker may call `request_decision` when a question blocks its next write. The parent does not open a human dialog itself: it queues the request and sends main a `subagent-decision` notice with candidate, worker, request, question, options, context and blocked scope. Main lists requests with `decisions`, then answers with `answer` (freeform text plus `basis` `user_answer` or `existing_authorization` and a traceable `reference`) or `decline` (with `reason`). Main may ask its own native `ask_user` first. Options are recommendations only; a custom answer is never mapped to an option.

The worker receives `answered` only with a recorded answer; `cancelled`, blank, timeout, declined and unavailable results are never approval. Steer cannot answer or unblock a request. Answers may be recorded while a job is paused but never resume it. Cancel, session reset, worker exit and job end settle pending requests exactly once. Limits: one open request per worker and four per session. The tool grants no tool, scope, server, commit or deploy permission. Foreground and direct headless runs get no decision tool.

Activation: saving these files does not change the running parent. The new tool exists only after a parent reload/restart at a safe point once active workers finish; reloading resets owned jobs. Existing jobs keep their toolsets.

## Provider cooldown (anthropic, openai-codex)

`provider-cooldown-guard.ts` wraps the `anthropic-messages` and `openai-codex-responses` stream functions (registered by `provider-cooldown-entry.ts` with the same provider ids and APIs, overriding only `streamSimple`). The guard classifies trusted HTTP observations (status plus bounded JSON body) into a shared store under `<agent dir>/run-state/provider-cooldown/`: 401 and body-typed 403 auth blocks are sticky until an explicit refresh; typed quota/rate/model cooldowns use trusted reset hints or the store defaults; 5xx, 529, prose and transport errors record nothing. Main requests during cooldown send no physical request. Parent pre-spawn checks move a replayable cooling primary (quota, rate or transient kind) or a probe-busy primary to its next declared fallback without spawning it; a blocked, unavailable or non-replayable cooling primary spawns nothing and does not fall back. A child refusal is replayed only when its text is exactly `provider cooldown cooling` or `provider cooldown probe-busy` and the parent's own store still reports that model replayable (cooling with a quota, rate or transient kind, or probe-busy); the parent validates its own store and never trusts prose. Tool-activity, abort and length outcomes are never replayed. Observations are provider-client-observed, not upstream-verified.

Commands: `/provider-cooldown` (status, provider-wide scope) and `/provider-cooldown refresh <anthropic|openai-codex>`, which runs the explicit credential refresh that unlocks an auth block. Status shows state, kind, source, deadline and `needsrefresh`; it never shows bodies, errors or auth values. Scope is limited: Codex WebSocket transport (`transport: auto`) is not covered by the HTTP observation, and other providers (for example Copilot, which mixes APIs) are not classified here. Remaining provider-cooldown roadmap items are pending; this section does not claim the full roadmap is implemented.

## Printed tool-call markup

A final assistant text that is raw tool-invocation markup (`<invoke name=...>` / `<parameter>` / `</invoke>` / `function_calls` tags indented 0-3 spaces, outside code fences; 4+ spaces are a code block) with no tool call in the last message is reported as `INCOMPLETE/UNVERIFIED (tool-call markup as text)` with the warning `This printed markup was not executed as tool calls; other recorded tool activity/partial writes may exist.` The text is kept unchanged. Detection is heuristic: it does not parse, extract or run markup, and it does not retry or fall back. Its only dispatch effect: a non-final chain step with markup is `isError`, and a DAG node with markup is not accepted, so its successors do not start. The cause (provider or model) is not established by this label.

## Safety guard
Main and every child run a `tool_call` guard (`safety-core.ts`). It blocks lexically risky shell operations (git publish/destructive, package publish or login, recursive forced delete, links, privilege/persistence, process kill, launching Pi, curl-to-shell, opaque encoded or eval forms), writes to config and git hooks, and direct reads or writes of secret files (`auth.json`, `.env`, `.npmrc`, keys and similar). Children load `safety-guard-entry.ts` after the pause gate and relay on every spawn; a missing guard file fails the launch closed. `request_authorization` is available only in the interactive TUI (`ctx.mode === "tui"` and a UI): the operator confirms up to 5 exact operations, each becomes a single-use in-memory grant bound to role, candidate and operation, with a 30-minute default TTL and 60-minute maximum. Grants are never written to disk or relayed, are revoked on abort and shutdown, and reach a child only through the `PI_SAFETY_GRANTS` environment variable, which is claimed and removed at spawn. Secret-file and non-grantable operations cannot be authorized. Block reasons show rule ids and an operation digest only, never the raw command.

Ordinary delivery needs no `request_authorization`: for a `release-engineer` child from user or package sources, launched in a candidate whose HEAD is already a valid non-protected feature branch with one verified github.com origin (fixed at spawn), the guard allows without any grant or lease a normal `git commit -m "<text>"` or `git commit -F "<abs .md/.txt>"` (double quotes required), a non-force feature-branch push, `gh pr create` and a same-owned `gh pr edit` (cwd = candidate root, strict grammar, same state and credential checks; no `GH_HOST`/`GH_REPO`). `-F` and `--body-file` files must sit under `<primary-parent>/worktrees/<origin repo name>/_evidence|_scratch/<task>/` (the legacy `<primary checkout basename>` group is also accepted) and pass the file checks (regular `.md`/`.txt`, at most 64 KiB, no credential-like content). Automatic PR edit (`gh pr edit N --repo O/R [--title "T"] [--body "B" | --body-file "ABS"]`, nothing else: no `--base`, reviewers, labels or state change) requires the repo to equal the live-verified origin repo and a live PR view showing the PR OPEN, headed by the task feature branch and strictly `isCrossRepository === false` (missing or null refuses); that structural check is the ownership rule, with no author lookup. PR merge and release creation have no automatic path: each needs its own action grant (below); a merge approval never authorizes a release and a release approval never authorizes a merge. Single-use `operations` grants refuse PR merge and release create (alone or batched). Optional `prBase` (a string on the single call or on each `tasks`, `chain` or `dag` entry; refused at the batch root and for null or invalid branch names, a base equal to the live feature branch, or any role other than a user/package `release-engineer`) binds that launch's PR base: `gh pr create` must use exactly that `--base` and an automatic `gh pr edit` is allowed only on a PR whose live base equals it. A known base travels to every spawn of that entry (fallbacks included) under its own `pushTargetBound` envelope key, never in `pushTarget`: a loader that predates it sees no push target and so blocks automatic push, commit and PR actions (fail closed) instead of silently dropping the base, and the current loader refuses a malformed, stripped, doubled or extra-field bound target. Omitting `prBase` keeps the legacy behavior (any syntactically valid base different from the feature branch); that is a documented residual risk, so when PR create/edit is authorized and the base is known, the orchestrator MUST pass `prBase` (the child cannot add it after spawn); commit/push-only delivery needs none, and a caller whose schema predates the field stays on the legacy residual. It narrows ordinary trusted delivery only, adds no approval prompt, reads no task text or child environment, and the envelope is protected launch transport, not an unforgeable or tamper-proof token. Local-only/no-publication instructions and passed required checks are orchestration gates applied by the orchestrator before it launches the release-engineer; the runtime guard cannot verify them. A refused commit whose only argument is a single unsupported `-m`/`-F` form gets a fixed hint naming the supported forms (no command or path echo); amend, `--no-verify` and `-a` get none. Do not mint any delivery grant for PR-only intent. `request_authorization` is for commands the guard genuinely blocked and other risky operations.

PR-branch push lease: `request_authorization` also accepts `push_branch: {branch, cwd?}` instead of `operations` (exclusive; no `role` other than `release-engineer`, no `ttl_minutes`). After one TUI confirmation (120 s timeout) it mints a session-only, in-memory lease bound to the canonical candidate, the feature branch and the single live `origin` push URL; no expiry, no disk or config write. An identical live binding is reused with "Already authorized" and no dialog. The lease reaches only `release-engineer` children spawned from user or package agent sources, through the `leases` field of `PI_SAFETY_GRANTS`, copied on every spawn (including fallback). A child may use it only for `git push origin BRANCH`, `git push -u origin BRANCH` or `git push --set-upstream origin BRANCH` through `bash` or `powershell` (rule `GIT_PUBLISH`, nothing else). Protected branches (`master`, `main`, `head`, `trunk`, `develop`, `release`, `releases`, `prod`, `production`, and their `release/*` and `releases/*` families), force, delete, mirror, tags, multiple push URLs, `pushurl`, a `receivepack` override, `push.followTags`, `remote.origin.mirror`, `push.recurseSubmodules` and `submodule.recurse` truthy or any value other than unset or false (`on-demand` and other non-boolean values fail closed), quoting, env prefixes, `-C`/`-c`, compounds and newlines stay blocked. Before each use the guard reruns fixed-argv git reads (repository top level, one push URL, branch resolves to `refs/heads/BRANCH`); any mismatch, timeout or error fails closed. `/revoke-authorization` and session shutdown withdraw leases; an abort keeps them. Running children keep their copies until exit; pause or cancel them with `subagent_control`. Push URL userinfo: any `http(s)://user@` or other credential-bearing form (token-only included) is refused with no secret in the message; public `ssh://git@host/` and `git@host:path` stay allowed. The candidate path must be displayable (no control or bidi characters) before confirm. Not reviewed: the branch content, pre-push hooks, `core.sshCommand`, credential helpers and `GIT_*` environment. Time-of-check/time-of-use between the live check and git's own push is not closed. Shortcut: a subdirectory cwd fails closed; upgrade by resolving the repository root explicitly.

Commit lease (`push_branch: {branch, cwd?, commits: true, artifact_dir?}`): the same lease also lets a trusted release-engineer child run normal commits on that branch. Enforcement applies only to `release-engineer` children from user or package agent sources (`gateCommits` in the `PI_SAFETY_GRANTS` envelope); every other role keeps the current behavior, so the commit rules are policy-only there. Upgrading a push-only lease to push+commit re-prompts once; repeating the same scope returns covered with no dialog. `artifact_dir` (absolute, under the candidate's `worktrees/<repo>/_scratch` or `_evidence` placement) binds the `-F` message files; it requires `commits: true`. Merge and release action grants never cover push or commits; commit scope needs its own confirm. Accepted commit forms only, through `bash` or `powershell`: `git commit -m "<message>"` or `git commit -F "<absolute approved .md or .txt file in artifact_dir>"`, with the message limited to ASCII letters, digits, space and `. , : _ / # ( ) + -` (1-200 characters). Denied and routed to a single-use exact grant or refused: `-a`, `--amend` and its abbreviations, `--no-verify`, `--allow-empty`, `--author`, `--date`, `--fixup`, `--squash`, `-c`, `-C`, signing, config overrides, wrappers, env prefixes, compounds, pathspecs. Before each commit the guard checks: `HEAD` is `refs/heads/BRANCH` in the candidate root (not a subdirectory), the live origin push URL matches the lease, no `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply` or `sequencer` state, and no redirect variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*`). Configured Git identity (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`) is preserved as the harness provides it. Not checked: repository hooks, global or system config, signing configuration, git aliases, and the content of staged changes. The `-F` file is checked once and can change before git reads it. This is a lexical matcher, not an OS sandbox. The lease stays session-only, has no expiry and is capped at 8 push or commit leases per session.

Scope and status: `/authorization` is read-only and secret-free. It lists live single-use grant counts by role and kind, each push and push+commit lease with its repo, branch, candidate, artifact directory and validity, and each merge/release grant with its repo, branch, base, PR, SHA (release also version, latest) and artifact directory, plus bounded reasons for invalid entries (for example `local branch is missing`). It shows no push URLs, tokens, commands or digests. `/revoke-authorization` withdraws single-use grants, leases and merge/release grants. Running children keep the snapshot they received until they exit; pause or cancel them with `subagent_control`. Reload or session end loses all state; nothing is persisted or synchronized live. Merge, force-push, delete, publish and deploy each need their own authorization and are not granted by a lease or commit scope.

Approved delivery command shapes (run each standalone from the candidate cwd, one per call, flags in any order, each once; the guard matches only these. Push, create and edit are automatic for the trusted release-engineer; merge and release need their own action grant):

```
git push origin feat/x
gh pr create --repo acme/widgets --base main --head feat/x --title "Add delivery grant" --body-file "D:/work/worktrees/app/_evidence/task/pr.md"
gh pr edit 12 --repo acme/widgets --title "Add delivery grant"
gh pr merge 12 --repo acme/widgets --squash --match-head-commit 0123456789abcdef0123456789abcdef01234567 --subject "Add delivery grant" --body-file "D:/work/worktrees/app/_evidence/task/pr.md"
gh release create v1.2.3 --repo acme/widgets --target 0123456789abcdef0123456789abcdef01234567 --title "v1.2.3" --notes-file "D:/work/worktrees/app/_evidence/task/notes.md" --latest
```

Merge and release grants (separate approvals): `request_authorization` accepts `delivery: {action, branch, base, pr, sha, cwd?, version?, latest?, artifact_dir?, bind?}` (exclusive with `operations` and `push_branch`; `role` only `release-engineer`; `ttl_minutes` rejected: session-scoped, TTL unsupported). `action` is `"merge"` or `"release"`; one grant carries exactly one action, so approving one never approves the other. Push, PR create and PR edit are not carried by any grant (they are automatic). Migration: the former combined `delivery: {branch, base, pr?, version?, latest?, bind?}` shape (no `action`, optional PR/version/binding) is rejected at the tool, at the store and at the child envelope loader (fail closed); the legacy `delivery`/`deliveryBound` envelope keys are refused and never reinterpreted, children now receive `deliveryActions`, and an older loader that ignores the new key gets no grant. Single-use `operations` grants for PR merge or release create are refused at request time (also inside a batch); push leases and commit leases are unchanged.

- **merge**: exact `pr`, the reviewed PR head `sha` (40 hex) and a mandatory `bind: {expect, exclude?}`: `expect` is the 64-hex fingerprint of the reviewed candidate, HEAD must be attached to the branch and `sha` must equal the bound HEAD. At mint the live PR must be OPEN, same-repo, on that branch and base with `headRefOid === sha`; it is re-verified after the dialog together with the fingerprint. A child's `gh pr merge N --repo O/R --squash --match-head-commit SHA40 [--subject "T"] [--body "B" | --body-file "ABS"]` matches only when `N`, SHA40 and the grant's PR and SHA agree, the live PR is OPEN, same-repo (`isCrossRepository === false`), has the bound base and head and `headRefOid` equals SHA40, and the live candidate (HEAD, branch, fingerprint) equals the bound state.
- **release**: exact `pr`, strict SemVer `version` (optional `v`, no leading zeros; `latest` optional) and `sha` = the release target (the PR's merge commit); never fingerprint-bound. At mint and at use the remote tag listing (`--exit-code --tags`) must report the tag absent (status 2; an existing tag, any other status or an error refuses, so `--target` is never trusted on an existing tag) and the approved PR is fetched directly with `gh pr view <approved number> --repo <grant repo> --json number,state,baseRefName,headRefName,isCrossRepository,mergeCommit`; it must be an object that is MERGED, strictly same-repo (`isCrossRepository === false`), has the approved number, head and base, and a merge commit equal to the 40-hex `sha`. Any error, array, null, primitive or missing field refuses. There is no PR list or history lookup, and there is no `mergedAt` or time fallback. A child's `gh release create TAG --repo O/R --target SHA40 --title "T" (--notes "B" | --notes-file "ABS" | --generate-notes) [--latest]` matches only the approved version and target.

Each grant is bound to the canonical candidate, the single live `origin` push URL, its github.com repo, the branch, the base and an optional validated `artifact_dir`. One TUI confirmation (120 s timeout) per new binding shows repo, PR, full SHA and the action; no time expiry (session-scoped, same `issuedAt`, no sliding); an identical live binding returns "Already authorized" without a dialog; at most 4 active grants, checked before the dialog and again after it. Main never uses them. Matching needs the command classified solely as `GIT_PUBLISH`, no compounds, and refuses on `GH_HOST`/`GH_REPO`, a read that throws, a 15 s timeout or invalid JSON. Live GitHub and Git reads run from the filesystem-root cwd with an explicit `git -C` candidate (PATH and global git/gh config are trusted, a documented assumption). Text: ASCII letters, digits, space and `. _ / # ( ) + -` (no colon); titles and subjects 1-120 characters; inline bodies and notes 1-500; credential-like text refused. Artifact files (`--body-file`, `--notes-file`) must be `.md` or `.txt` regular files with one link, 1 to 65536 bytes, no NUL, inside the approved `artifact_dir` (absolute forward-slash folder under `worktrees/<repo>/_scratch` or `_evidence/<task>`, existing, not an alias or junction, no 8.3 `~<digit>` segment, not overlapping the candidate). `/revoke-authorization` and session shutdown withdraw them; an abort keeps them; running children keep their copy until they exit, so stop them with `subagent_control` first for immediate effect. They authorize no other tag, force, branch deletion, other refs, npm, deploy or API calls.

Merge fingerprint binding (mandatory for merge, never for release): `delivery.bind: {exclude?, expect}` with `expect` required binds the merge grant to the candidate state the operator reviewed, requested after the final commit. At mint, HEAD must be attached to `refs/heads/<branch>`; the grant records the full HEAD (equal to `sha`), the candidate fingerprint (HEAD + typed status records for staged, unstaged and untracked paths + the unfiltered staged-diff digest + the exclusions) and `exclude` (at most 8 relative paths, no `..`, `.git` or tracked path). `expect` (64 hex) refuses the mint unless the live fingerprint equals it. The state is computed before the dialog, shown in it, recomputed after confirmation and compared; a change in between mints nothing. A merge matched against the grant recomputes the state and is refused when HEAD, branch or fingerprint differ or anything is unreadable, UNSUPPORTED (nested repository, unreadable or non-UTF-8 path) or over the limits (5000 records, 64 MiB hashed, 15 s per git call). A new bound approval for the same PR and SHA replaces the older record after a fresh confirm; use never rebinds. Git runs with fixed argv from a neutral cwd (`-C`), `core.fsmonitor=false`, `--no-optional-locks`, `--no-ext-diff`, `--no-textconv`, so candidate git config runs no fsmonitor, diff or textconv program in the helper's own calls. Because a delivery fingerprint shares this preflight with cleanup, the helper first refuses (fixed `RangeError`, before `ls-files`/`status`) ANY repository-local or worktree-scope `core.fsmonitor` entry (hook, true, false, valueless, any casing, or through an include), whatever its value; this is intentionally conservative and also refuses delivery fingerprints for such checkouts. Entries from system, global or command scope are trusted and never refused; malformed config output or a Git failure other than "no entries" also refuses. Before any Git command reads the working tree the helper fails closed (the mint is refused and a stored grant stops matching) on: a repository-local `filter.*` driver (filters from system/global config stay trusted); index flags that hide or skip tracked files (assume-unchanged, skip-worktree, sparse checkout, submodule/gitlink entries); a symlink or junction as a parent of a tracked path; and on Windows any non-ignored symlink or junction Git could enter during untracked discovery (lstat walk, ignored directories pruned through `git check-ignore`, 200000 entries cap). These are pathname checks, not a fix for the check-then-use race. Ignored files and `.git` internals are never read: ignored files are outside the fingerprint, and fetch, ref or upstream updates do not invalidate. Children receive the records under the `deliveryActions` envelope key and recompute the state themselves. `/authorization` labels the grant `fp <12>, excl N (not rechecked in status)`. Limits: the check is not race-free: the command runs after the guard allowed it, so a parallel tool call or hook can still change state before the merge executes (the merge is additionally pinned to the SHA the server enforces through `--match-head-commit`). The same user, scripts and the operator's shell are outside the guard, and free-form reviewer approvals are not enforced by it. A merge grant never covers push or commits, and no pull, checkout or commit may happen between approval and merge (re-authorize instead). Legacy combined delivery grants are not accepted. Regression: `DELIVERY_TEST_SCRATCH=<scratch> node --experimental-transform-types --test agent/extensions/subagent/tests/delivery-bound.test.ts`.

Automatic post-merge checkout cleanup (narrow, checkout only): the `subagent` tool accepts a root `cleanup: {checkout, branch, base, pr, headSha, mergeCommit, quiescent: true}` for a single-mode launch of the trusted (user/package) `release-engineer` with `cwd` = the primary checkout; any other mode, role or shape is refused before launch. The request is only a selector plus main's quiescence declaration. Before minting, the runtime independently proves: exact `<primary-parent>/worktrees/<primary name>/<task>` placement, no link or alias, a linked worktree of that primary, HEAD attached to the approved branch at the approved head, the single live origin binding, an unlocked unique registration with no nested registration, the same hardened Git preflight as fingerprint-bound delivery (any repository-local or worktree `core.fsmonitor` setting, repository-local filters, assume-unchanged/skip-worktree/sparse index entries, gitlinks/submodules and linked ancestors or directories are refused before any working-tree read, because the permitted `git worktree remove` itself would run a configured monitor and could destroy data it creates; the proof's own Git calls disable fsmonitor, no optional locks) and a status through that hardened helper with `--ignored` empty (any tracked, untracked or ignored content, `.serena` and caches included, is retained, never assumed disposable; Git's own non-force removal is not a byte-safety backstop for ignored or hidden data), no link, hard link or nested repository inside, and a live same-repo PR that is MERGED from that branch/base with `headRefOid` equal to the head and the approved `mergeCommit` (squash-safe: no ancestry check). The slow PR read runs FIRST (it needs only the grant fields); identity, registration, preflight, link walk and status run last, immediately before the scope is minted or consumed, so a write during the PR read is refused. Runtime owner tracking (worker cwd recorded before spawn, ended only after the process closed, in memory) must show every worker that touched the folder terminal, no owner job running or paused and a release-engineer delivery owner; unknown ownership, a session restart or a main cwd inside the target retains. The scope is single-use, expires after 10 minutes, is revoked by abort (`revokeAll`, observed at `agent_settled`) and shutdown while it is still unclaimed, travels only in the cleanup launch's envelope (`cleanupActions`; no delivery or push scope, never in a fallback spawn, refused if the launch cwd is not the primary or overlaps the target) and reserves the folder so no new worker starts in or above it. Reservations are keyed by scope: an aborted `agent_settled` cancels each live cleanup job through the existing job abort signal (best-effort SIGTERM, then a forced kill after 5 s) and releases only UNCLAIMED reservations; a claimed one persists until the child's close is confirmed and is then released only after a clean exit (an aborted, killed or failed close keeps the folder reserved until the 10-minute TTL because a shell the child started cannot be observed); `session_start` never drops a claimed reservation. A second cleanup request for a reserved folder is refused. The child guard then allows exactly `git worktree remove "<absolute forward-slash path>"` from the primary, after repeating every live check, and consumes the scope. Flags, `-C`, `--force`, prune, branch deletion, chains, redirects, other paths, artifact folders (`_scratch`, `_evidence`) and replays stay blocked. Pending state is derived by the runtime, not by child text: after a background job completes a separate `subagent-cleanup-pending` message, and `subagent_control list` as a second text block, carry `CLEANUP_PENDING` with PENDING_UNVERIFIED or RETAINED entries: runtime-only metadata from a merge delivery grant of this session plus the owner records, with no Git, `gh` or filesystem access, no `mergeCommit` and no `launchCwd`, and the always-RETAINED artifact folders. Nothing in it is verified, merged or ready; when main actually schedules the cleanup launch it queries the PR explicitly and live for `mergeCommit` and uses its own primary, and the unchanged strong mint and guard rechecks still decide. Main must still launch the cleanup release engineer itself; the runtime never launches or calls model tools. Limits: the guard decides before the command runs and is not atomic with the shell (a write between the final local proof and the command is a documented residual; Git's refusal covers only tracked/untracked dirt it can see), abort is observed when the main agent settles, not at the instant of abort, termination is best-effort, a command already running or a shell grandchild is neither recalled nor tracked (no child revocation channel exists), `core.fileMode=false` and end-of-line conversion can hide mode-only or EOL-only edits from status, PATH and global Git config are trusted, main-side owner state cannot be re-read by the child at removal time (mitigated by the folder reservation and the 10-minute scope), PRs merged outside this session's delivery grants are not listed as pending, and `/authorization` shows only a pending-scope count. Regression: `node --experimental-transform-types --test agent/extensions/subagent/tests/cleanup-grant.test.ts agent/extensions/subagent/tests/cleanup-runtime.node.ts agent/extensions/subagent/tests/cleanup-dispatch-runtime.node.ts` (the last drives the real registered tools, owner tracking and the spawn seam, offline).

Known limits: this is a bounded lexical matcher, not an OS sandbox. Scripts, environment indirection, shell aliases, the user's own shell and trusted extension code can bypass it; the operator's environment is not a hostile-process boundary. Known unsupported lexical forms (verified unflagged): `iex 'rm x'`, `Invoke-Expression 'git push origin main'`, `npm exec -- npm publish`, `yarn npm publish`, `find . -exec /bin/rm x ;`, `git checkout -f`, `gh api --method=POST repos/a/b/x`. Unquoted `<`, `>`, `>>`, `>|`, `>&` and `&>` (optional fd digit) end the word before them, so `echo x>auth.json` and `cat<.env` are classified as secret access. `>|` and `>&` are redirections, not pipes or background separators: `echo x >|settings.json` and `echo x >&.git/config` classify as config writes, while `echo x | cat` and `echo x |& cat` keep separate segments. A backslash-escaped `>` is literal: `echo a\>|git push` and `echo a\>&git push` split as a pipe or background separator and classify as `GIT_PUBLISH`, Git Bash on Windows collapses each backslash pair in argv before the shell parses the command, so a run of n backslashes reaches the shell as ceil(n/2) (probed with `usr/bin/bash.exe`). `classifyShell` therefore returns the union of the raw text and the pair-collapsed text. A git form (`>|` or `>&` then `git push`) is blocked for one, two, three, five or six backslashes (not zero or four); a config form (`settings.json`, `.git/config`) is blocked for zero, two, three, four or six (not one or five). Intentional over-blocking: script-file bash reads the two-backslash git form as a redirection, and the union blocks it anyway. Shortcut: backslash parity only, not a quote-aware escape lexer; the collapse applies on every platform and shell, so PowerShell or POSIX text with backslash pairs can over-block; upgrade with a real shell lexer and a per-shell transport gate. Escape and wrapper readings: `classifyShell` and the merge/release recognizer share one bounded union of readings, raw and backslash-pair-collapsed text each read with no escape, POSIX backslash escapes and PowerShell backtick escapes, so escaped quotes in a `-c` payload (`bash -c "gh \"pr\" ..."`), `g\h`, `bash -xc`/`sh -ec` flag clusters (also ksh, ash, csh, tcsh, fish) and PowerShell `` ` `` escapes are classified; `env` is supported only as `env [NAME=value ...] command args` (any word containing `=` and not starting `-` is an assignment, so `a.b=1` counts). Any env option (`-i`, `-u X`, `-S`/`--split-string`, `-`, `--`, clusters, attached or long forms, also after assignments) is refused as `OPAQUE_UNPARSEABLE` (not grantable); env option grammar is never modelled, so benign `env -i node` and `env -S 'node -v'` are over-blocked on purpose. Still unsupported (lexical indirection, verified unflagged): `echo '...' | bash`, here-strings, `iex`/`Invoke-Expression`, aliases, scripts, variables and stdin; the union is not a shell parser and may over-block exotic benign text. Also unsupported (verified unflagged): glob targets (`echo x > agent/sett*s.json`) do not match `settings.json`; variables are not expanded (`V=settings.json; echo x >|$V`); and only direct credential basenames (`auth.json`, `.env`, `.npmrc`, keys) classify as `SECRET`, so backup or renamed copies such as `agent/auth.json.bak` may not classify. Any path component of the target or of the cwd (a relative target is joined with the cwd first) containing `~` followed by a digit is refused as `PATH_AMBIGUOUS` (not grantable). Shortcut: this also refuses literal names such as `~1`, and relative reads from an 8.3-alias cwd; `~/` and `a~b` are unaffected. Unsupported lexical forms remain documented here and are not covered by the matcher. Coverage is builtin-only: the hook inspects `bash`, `powershell`, `write`, `edit`, `read`, `grep`, `find` and `ls`. MCP, Serena and QMD tools are outside this guard. Grants transfer exactly once: `claimChildGuard` removes each matching unexpired grant for the role and candidate at spawn and passes it only to that child. Each logical job has one claim window: its first actual spawn closes it, even when zero grants match or the spawn fails. Fallback and retry spawns of that job never claim, so no grant is injected mid-run; a pre-spawn cooldown skip does not close the window. A grant minted after that spawn is claimed only by a new job. Broad recursive searches (`grep`, `find`, `ls`) of directories containing secrets are not blocked; only a direct secret path given as the target of `read`, `grep`, `find` or `ls` is refused. Credential material is not grantable: use the operator out of band. This section documents the working-tree source; it does not activate the profile, reload a running Pi, or make any npm package claim.

Manual config scan (read-only, never reads `auth.json` or `settings.json` contents): `node scripts/scan-harness-config.mjs [--root <profile dir>]`; it exits 1 on any ERROR finding.
