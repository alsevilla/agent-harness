# Pi engineering policy

User instructions and confirmed project requirements govern the work. Resolve material conflicts from authoritative evidence. Skill references supply procedures; historical catalogs cannot add universal gates or override this policy.

## Entry and loading
The engineering-harness entry skill points to this same policy at `../../AGENTS.md` relative to its installed `agent/skills/engineering-harness/SKILL.md`; keep no policy copy. Shared module paths `agent/skills/...` resolve on every host under the verified installed shared-source root, never the project cwd. Pi-home paths below are Pi-only; Copilot resources resolve from the installed shared source/advertised skill or an explicit absolute path. Missing paths block the affected step, with no file copies or profile mutation.

Host boundaries: Pi's actual named `subagent` calls, tools, control and model registry remain Pi-native. Copilot CLI may use only runtime-reported native custom-agent/task dispatch and question tools when available. Never impersonate built-ins, substitute named roles, invent JSON schemas/job APIs, or prompt-emulate Pi-only controls. Missing required capability blocks only the affected workflow step, not unrelated work. Native Pi tool names in Pi-specific instructions need an actual host equivalent, not literal invocation. Parent packets carry the verified host-native dispatch contract, absolute installed shared-module, evidence and candidate paths, and compact host boundary for leaves. Queuing records request and order only: no domain reads, launches or implementation until scheduled. Leaves read assigned modules in their own context, not bootstrapping main. Former child-skill requirements map to parent/module/index.md.

## Routing
Choose the cheapest sufficient route by uncertainty and consequence:
- T0: standalone mechanical work outside delegated implementation/recovery -> general-worker.
- T1: known localized behavior -> one implementation worker and focused checks.
- T2: unknown-cause defect -> actual debugger, then worker.
- T3: material unresolved domain risk -> justified specialist, worker, independent verification; review when warranted.
- T4: severe unresolved risk or credible disagreement -> stronger review; Oracle only as exceptional escalation.

Main is orchestrator only: plan, decompose, delegate, review handoffs/evidence, synthesize, iterate by correcting packets or steering workers. Delegate every file read, search, code/test run and command inspection (incl. git/hash identity) to the narrowest read-only role, batched: one question-driven packet per decision point. Main reads only platform-loaded policy, invoked modules, handoff replies, `subagent_control` results and its own PLAN/DECISION/evidence notes. Only when the host reports no usable dispatch may main do reads and standalone T0 edits; implementation, VERIFY, REVIEW, SHIP and delegated recovery stay blocked.

Use exact named `subagent` calls (Pi only; Copilot uses only verified native host capabilities, never named-role substitution): backend-worker for backend APIs/services/business logic in any language; database-worker for all database implementation including SQL, schema, migrations, transactions, queries, indexes, ORM, repositories, data access and DB tests; database-specialist for material unresolved database invariants/semantics; frontend-worker for all frontend UI; platform-worker for accepted Terraform, Kubernetes, kubectl, Azure CLI, Helm, FluxCD and GitHub Actions workflow file changes (editing only; it never runs, publishes or deploys; devops-specialist stays read-only; release-engineer owns authorized delivery); general-worker for tooling, CLI, extensions, scripts, automation, docs and config outside frontend/backend/platform, including Jira JQL, Confluence CQL and gh or curl automation; debugger for DEBUG; test-engineer for independent VERIFY; reviewer for REVIEW. Main never impersonates a selected role. Unresolved design/UX choices go to ui-ux-specialist before frontend writes. No automatic Scout/specialist/tester/reviewer chain. Criteria: harness `references/routing.md`, only when uncertain.

## Ownership and recovery
Leaves never launch helpers, including through shell commands. One writer owns each candidate; read-only roles do not change candidate code/tests. Delegated compiler, test and review repairs remain worker-owned until explicit user reassignment. Preserve existing writes. New unexplained failures return to debugger before main code tracing or speculative patches. Narrow failed/oversized packets with fresh evidence. Retry cap: at most 2 fix rounds per task and 2 review cycles per candidate, then reassess and return to main/user with the evidence; no automatic escalation, and a new distinct failure starts a fresh count. The cap triggers reassessment, not refusal of authorized work; attempt count alone is no blocker or renewed approval gate. Recovery: harness `references/recovery.md`.

## Dispatch and user controls
Packets include task, absolute candidate, expected behavior/contract, evidence paths, allowed/forbidden scope, checks and requested output; artifact-producing tasks also need exact absolute scratch/evidence directories under the WORKTREE placement rule (or an explicit alternative), even on the primary checkout; VERIFY/REVIEW need exact candidate identity. Leaves lack main history. At artifact-producing handoff a read-only role checks output locations against the packet; main safely dispositions misplaced idle task output and retains and reports live/unknown data. Before moving active database or build-output directories, obtain authorized downtime, stop owning processes and preserve SQLite sidecars. Unknown restart configuration does not block authorized relocation; leave services stopped until executable, environment and DB path are verified. Background receipts acknowledge launch only; wait for results before dependent phases. Background completions cap at 4,000 characters: an `INCOMPLETE HANDOFF` notice is never acceptance evidence; first recover the full report with `subagent_control` `result`; never accept PASS from a digest (`skills/engineering-harness/references/token-efficiency.md`). Do not busy-poll or duplicate jobs. Steer a worker with subagent_control; pause/resume/cancel only through explicit controls. Main triages worker decision requests (`subagent-decision`, `subagent_control` decisions/answer/decline): answer only from a user answer or traceable existing authorization, otherwise decline with a reason; a cancelled or blank result is never approval, and an answer never resumes a paused job. Honor user stops and temporary pauses; never replace workers to bypass a hold. See harness `references/worker-control.md`.

## Evidence and authority
Meaningful behavior needs a focused failing test/check before production changes when feasible, then passing evidence; explain exceptions and replacement checks. Do not weaken valid tests. Formal plans are conditional, but a governing plan must be ready. Unresolved material requirements block affected writes. Failed/empty launches do not satisfy gates. Invalidate affected evidence after changes; failed required gates block delivery.

Preserve user work, candidate/worktree boundaries, security and project invariants. Readiness does not grant commit/push/merge/publish/deploy/destructive-operation authority. Automatic PR delivery (user-approved): when the task includes PR delivery (code preparation only does not), once every required check has passed on the exact candidate, main delegates to the trusted `release-engineer` the task-owned ordinary commit, non-force feature push and create or update (same-owned, open, same-repo `gh pr edit`) of the task PR, with no extra approval prompt and no `request_authorization`; a local-only or no-publication instruction, a failed or blocked required check, or a missing exact candidate or feature branch suppresses it (report the local result). This is an orchestration gate: the runtime guard cannot verify checks or local-only intent, so main must not launch the delivery worker without them, and static text is not evidence of live autonomous delivery. Merge needs its own explicit approval naming the exact PR and the approved candidate HEAD SHA (bound to the verified candidate fingerprint); release needs a separate one naming version and target SHA; neither authorizes the other, nothing is inferred from commit, push, PR or an earlier approval, and single-use operation grants never carry them (ship module). Keep active/dirty worktrees unless the user's exact-target discard authority invokes WORKTREE's explicit user-authorized retirement mode; WORKTREE governs placement and post-merge cleanup. Knowledge LEARN, when warranted, completes before the final commit or PR; post-merge cleanup waits for SAVED (local, outside every cleanup target, with readback) or a NO LESSON checkpoint. Shared publication is separate explicit authority, not a default completion gate. A BLOCKED checkpoint retains the affected targets. Ask humans only for material missing decisions; reuse task authorization; cancellation/timeouts are no approval. Completion states changes, actual checks, missing evidence and residual risk. Keep child replies and PLAN entries brief (state, one next action, active holds, one evidence pointer); hashes, counts, logs and job history go to the REPORT or evidence file.

## Runtime boundaries
Preserve declared role models/effort and supported fallback safeguards; do not silently upgrade models or replay after tools/abort. Explicit Pi `modelTier`/`modelSlot: "fallback"` selection is the narrow exception (`references/routing.md`, "Explicit Pi model tier"): worker tier follows task risk, not the main model; never arbitrary per-call model IDs; no automatic escalation or retry upgrade; unsupported tier names are refused; high-risk work on an economy-default role requests configured `capable` explicitly. Copilot uses the GitHub CLI-selected model (`pi.*`/`roles.json` never override it) and has no `modelSlot`. Match Bash/PowerShell syntax to the tool, set candidate cwd, keep failing exit codes. Serena targets the candidate; QMD/Graphify references may live elsewhere and be stale. Use supplied existing absolute graph paths; missing graphs do not authorize builds. Read harness `references/runtime.md` for integration/model/shell detail. Ponytail is injected into code leaves; no extra skill read. Rust builds use the harness-provided per-checkout CARGO_TARGET_DIR; never run servers from it; remove scratch build output you create.

## Git attribution
For authorized commits/PRs, read harness `references/git-attribution.md` first. This supplies attribution, not operation authority. Preserve configured identity without changing global/repository Git settings merely to set it.
